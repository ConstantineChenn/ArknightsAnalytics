# ACG 周边商业化运营面试与项目专业化手册

> 面向周边商业化运营、商品运营、电商运营与运营数据分析实习岗位。本文档用于持续补充面试知识、项目证据和场景题答案。

## 1. 岗位本质

周边商业化运营不是单纯维护商品信息，也不是只根据角色人气做周边，而是完成以下经营闭环：

```text
IP与用户洞察
→ 角色和品类选择
→ 定价、成本与库存规划
→ 上架、直播与活动执行
→ 成交、退款和库存监控
→ 数据复盘
→ 下一轮选品与补货
```

与游戏测试岗位相比：

- 游戏测试关注质量、风险、缺陷复现与版本准入。
- 周边商业化运营关注需求、商品、渠道、库存、收益与经营复盘。
- 两者共同要求证据意识、边界分析、跨团队协作和问题闭环。

## 2. 岗位能力模型

### 2.1 ACG 与 IP 理解

- 理解角色人气、剧情曝光、游戏强度、视觉设计和粉丝购买力之间的差异。
- 能区分短期事件热度与长期稳定需求。
- 能判断角色与徽章、亚克力、纸品、毛绒、服饰和手办等品类的适配关系。
- 理解官方、授权、联名和同人商品在成本、权益与用户认知上的差异。

### 2.2 商品运营

- 角色选择与商品立项。
- SPU、SKU、规格、条码和商品主数据维护。
- 引流款、主力款、利润款、形象款和复购款的货盘结构。
- 成本、售价、毛利、生产周期、最低起订量和库存风险。
- 现货、预售、补款、尾款和延期履约。

### 2.3 电商与直播

- 商品上架、价格、优惠、库存和状态核对。
- 直播前的人、货、场、数据和应急预案。
- 商品曝光、点击、加购、下单、支付、退款的转化漏斗。
- 根据引流、承接、转化、利润和复购目标设计直播货盘。

### 2.4 数据分析

- 使用 Excel、SQL 和 Python 完成数据清洗、连接、聚合、排名和报告输出。
- 理解 GMV、毛利、转化率、售罄率、退货率、库存周转和投产比。
- 能区分真实数据、公开代理指标、人工规则和模拟数据。
- 面对缺失、重复、截断和偏差数据时不制造伪精度。

### 2.5 执行与协作

- 与设计、采购、供应链、仓储、客服、直播和市场团队同步信息。
- 对商品名称、规格、价格、库存和发货时间保持细节敏感。
- 能处理临时任务、直播事故、库存异常、价格错误和用户投诉。

## 4. 项目专业化定位

### 4.1 Business Goal

单个平台的播放量不能直接代表周边购买需求。老内容会自然积累曝光，不同平台的用户互动含义也不同；如果仅根据声量选品，可能造成热门角色过度备货、长尾角色需求被忽略或高客单商品库存积压。

项目建立以下可解释决策链路：

```text
官方内容热度
→ 跨平台一致性
→ 淘宝商业信号
→ 内容与商业缺口
→ 品类和价格带
→ SKU组合与库存风险
```

### 4.2 当前数据资产

| 数据层 | 当前规模 | 主要用途 |
|---|---:|---|
| Bilibili 官号角色内容 | 30 条 | 长期角色热度基线 |
| Weibo 官号近期内容 | 100 条 | 近期曝光与跨平台验证 |
| Xiaohongshu 品牌生态 | 4 组 | IP整体种草环境观察 |
| Taobao 公开商品快照 | 84 条 | 价格、供给和销量代理验证 |
| 角色主数据 | 30 名 | 内容与商业统一分析主键 |
| 模拟 ERP SKU | 180 个 | 选品、毛利和库存方法演示 |

### 4.3 当前技术资产

- Python ETL 流水线。
- Pandas、NumPy 指标计算。
- 角色别名、异格名和单字边界治理。
- 《明日方舟》与《明日方舟：终末地》IP隔离。
- SQLite 5个业务视图、20组分析查询和6个复合索引。
- CSV、SQLite、Excel、Markdown和图表多格式输出。
- 20项pytest自动化测试，总覆盖率75%。
- 56个固定商品ID注册表及30个新约能天使首轮复采队列。
- 匿名用户调研质量门禁、样本等级和自动分析流水线。
- 新约能天使六层证据选品案例，当前状态为`conditional_pilot`。

### 4.4 内容热度模型

```text
Heat Score
= 40% 播放速度
+ 30% 加权互动率
+ 15% 收藏率
+ 15% 分享率
```

并进一步拆分：

- Reach：传播规模。
- Momentum：发布时间校正后的传播速度。
- Engagement：综合互动质量。
- Intent：收藏、投币和转发等深层意向。
- Discussion：评论与弹幕讨论强度。
- Consistency：跨平台一致性。
- Confidence：样本量和平台覆盖形成的数据可信度。

### 4.5 淘宝商业信号

```text
Commercial Heat
= 35% Demand Proxy
+ 25% Supply
+ 20% Search Visibility
+ 10% Price Power
+ 10% Assortment Breadth
```

- Demand Proxy：公开收货人数下界。
- Supply：可稳定追踪的自然商品数量。
- Search Visibility：搜索排名衰减后的可见度。
- Price Power：角色商品价格承载能力。
- Assortment Breadth：角色商品覆盖的品类宽度。

### 4.6 SQL 决策成果

SQL不只用于查询数据库，而是承担运营计算层：

1. 使用 JOIN 统一角色热度、淘宝商业信号和SKU经营指标。
2. 使用CTE拆分价格带、市场集中度和库存风险。
3. 使用ROW_NUMBER完成角色内、品类内和风险队列排名。
4. 使用PERCENT_RANK比较同品类SKU的相对位置。
5. 使用CASE WHEN生成业务象限、商品定位、风险等级和推荐动作。
6. 使用条件聚合和NULLIF计算加权转化率、售罄率和退货率。
7. 使用EXPLAIN QUERY PLAN验证复合索引真实命中。

当前输出：

- 3名核心商业角色。
- 12名内容热、商业供给待验证角色。
- 15名低成本观察角色。
- 10个直播核心模拟SKU。
- 57条可进入固定商品ID时间序列的淘宝记录。
- 淘宝基线样本Top 10销量代理集中度53.72%。

### 4.7 数据边界

- 公开收货人数是销量下界代理，不是精确销量。
- `100+`按100记录，并标记为截断数据。
- 模拟ERP只验证分析方法，不代表真实GMV、利润或库存。
- 未观察到淘宝商品只代表当前样本未覆盖，不能解释为没有需求。
- 正式业务结论仍需要收藏加购、订单、退款、库存和用户调研数据。

## 5. 项目介绍口径

### 5.1 一分钟版本

我独立完成了一个《明日方舟》IP角色热度驱动的周边选品分析项目。项目没有直接把播放量当成购买需求，而是对B站、微博等公开内容进行发布时间校正，构建传播、增长、互动、深层意向和讨论五类指标；随后接入淘宝公开商品快照，从需求代理、供给、搜索可见度、价格承载和品类宽度构建商业信号，并与内容热度形成选品象限。工程上使用Python完成数据清洗和报告流水线，使用SQLite建立5个业务视图和20组分析查询，最终输出角色验证队列、价格带、SKU组合和库存风险结果。项目明确区分公开、人工和模拟数据，避免将代理指标描述成真实销量。

### 5.2 三分钟版本结构

1. 业务问题：单一内容热度不能直接指导选品。
2. 数据来源：B站、微博、小红书生态、淘宝公开商品。
3. 数据治理：时间校正、别名治理、IP隔离、搜索相关性和截断标记。
4. 分析方法：内容热度、商业热度、内容商业矩阵和SKU评分。
5. 工程实现：Python、Pandas、SQLite、SQL、pytest和自动报告。
6. 量化结果：30名角色、84条淘宝快照、56个固定SKU、180个模拟SKU、5个视图、20组SQL、20项测试。
7. 业务结论与限制：输出验证优先级，但不声称真实市场份额。

## 9. 项目专业化路线

### P0：当前必须完成

- 保持所有指标、数据来源和模拟边界可追溯。
- 完善README、方法文档、数据字典和项目讲解口径。
- 为项目核心结果准备SQL和原始数据证据。
- 准备一个成功洞察案例和一个数据质量修复案例。

### P1：时间序列商业验证

- 固定商品ID，每周复采价格、收货人数档位和状态。
- 计算销量档位跃迁、价格变化、上新率和下架率。
- 区分新品、增长、稳定、衰退和售罄生命周期。
- 建立角色和品类的商业动量指标。

当前已完成固定SKU注册表、复采队列、纵向指标与证据等级；仍需按真实日期完成第二至第四期采样。

### P2：用户调研

- 建立角色偏好、品类偏好、价格接受度和购买频次问卷。
- 区分核心玩家、轻度玩家、周边收藏用户和非玩家消费者。
- 将“表示愿意购买”与真实预售转化分开验证。

当前已完成匿名问卷字段、质量门禁、导入脚本与分析报告；尚未导入真实受访者答卷，因此不报告虚构购买意愿。

### P3：真实经营数据接入

- 接入授权的订单、库存、退款和履约数据。
- 将模拟转化率、毛利和库存风险替换成真实指标。
- 建立补货、清仓、预售和下架规则。

### P4：竞品与渠道分析

- 对比不同ACG IP的品类、价格带、上新节奏和联名策略。
- 分析淘宝、抖音、B站会员购和线下展会的渠道差异。
- 建立直播货盘、活动排期和渠道投放建议。
